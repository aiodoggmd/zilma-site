# Дизайн-система гид-виджетов статей (2026-08-17, эталон — Koleston Perfect)

Пользователь попросил повторить оформление официальных PDF-инфографик Wella (пропорции смешивания, круговые «часы» выдержки, шаги аллерготеста, шкалы) **не картинкой-скриншотом, а настоящим контентом** — выбран «Вариант C»: свой набор CSS/HTML-виджетов в палитре сайта, а не копия фирменного дизайна Wella. Реализовано и подтверждено пользователем на статье `2026-08-13-koleston-perfect.md` — **это теперь стандарт для оставшихся 11 статей**, не изобретать заново, переносить как есть.

**Где лежит:** все стили и JS — в `Site/src/pages/articles/[id].astro` внутри `<style>`/`<script>` (общие для всех статей, т.к. это динамический `[id].astro`, не per-article файл). Контент-разметка — сырой HTML прямо в `.md` файле статьи (Astro пропускает raw HTML в markdown как есть).

**Набор виджетов (классы, все под `.prose :global(...)`):**
- `.wheel` (+ `.sm`, `.triple`) — кружок-«колесо» на `conic-gradient`, заливка `var(--color-pastel-red)`/`var(--color-pastel-blue)` (не насыщенный `--color-red`/`--color-blue` — см. ниже про палитру). `--split` (CSS-переменная, %) задаёт реальную долю — для пропорции смешивания (1:1 → 50%, 1:2 → 33%) и для времени выдержки (без тепла : с теплом). Не декоративно, а по факту, каждый раз считать реальное значение, не ставить наугад.
- `.mix-card` — крупная карточка: колесо-пропорция слева (растёт на всю высоту, `grid-row:1/3`), текст+список справа сверху, полоска-таймер (свой маленький `.wheel` + текст) снизу. Для разделов с несколькими % окислителя и списком эффектов (пример: «Схема смешивания с Welloxon Perfect»).
- `.service-card` — компактный вариант в один ряд: колесо + заголовок (+ `.ratio-tag` пилюля с пропорцией) + описание + время. Для разделов «один рецепт = одна карточка» (уходовые техники, глянцевание, пастельное тонирование).
- `.frac-list` — список-строки с маленьким `.wheel.sm` слева, для долей/пропорций без отдельного рецепта (пример: «добавить 1/3 объёма»).
- `.timer-chip` — инлайн-пилюля колесо+текст, для одиночных упоминаний времени вне карточки (пример: «Нанесение на отросшие корни»).
- `.step-flow` — сетка шагов с нумерованным `.badge`-кружком и фото/иконкой под ним (аллерготест). Если фото шага нет или оно битое — `.step-icon` (пунктирный плейсхолдер с коротким текстом) вместо `<img>`, не пропускать шаг молча.
- Таблицы (`table`/`th`/`td` — глобальный стиль, без класса) — автоматически получают оформление сайта (шапка `--color-panel`, чередующиеся строки), просто использовать обычный markdown-синтаксис таблицы.
- `.scale-row`/`.scale-bar` (`.depth`, `.tone`) — горизонтальная шкала-градиент вместо картинки-диаграммы, когда официальной картинки нет или она битая (пример: «Система нумерации оттенков» — 2 шкалы вместо несуществующего `numbering-system.png`).
- `.callout` — акцентная врезка (цветная левая полоса) для отдельных концептуальных определений без пропорции/времени (пример: «Дополнительный цвет», «Кривая осветления»).
- `.checklist`/`.check-icon` — ряд пилюль с галочкой для чекбокс-сеток «область применения» из официальных PDF-инфолистов Wella (пример: Color Touch, страница 1 — 5 колонок с зелёными ✓ под разными техниками). Один `<li>` = один официальный пункт, отмеченный галочкой в источнике — не добавлять пункты без галочки в PDF и не пропускать отмеченные.

**Лайтбокс (увеличение картинок по клику)** — общий для всех `.prose img`, JS в конце `[id].astro`: клик открывает картинку в оверлее на весь экран в реальном разрешении, второй клик закрывает. Добавлен, потому что палитра оттенков (`palette.png`, обычно ~2400px) нечитаема в узкой колонке статьи (760px) без этого. Работает уже на все статьи автоматически (общий файл), ничего дополнительно включать не нужно — просто не убирать `cursor:zoom-in`/`.lightbox-overlay` при правках стилей.

**Палитра для виджетов — только переменные из `global.css`, никогда не изобретать свой hex:** `--color-pastel-blue: #bcd8f2` / `--color-pastel-red: #f3c1c9` (те же, что фон стат-панелей в блоках прайса `PriceBlock.astro`) — заливка `.wheel`. `--color-red-dark` — сплошные акцентные значки (`.step-flow .badge`, `.checklist .check-icon`). **Реальный инцидент 2026-08-17:** для галочек `.checklist` был добавлен произвольный зелёный `#4d9463`, которого нет в палитре сайта — пользователь поправил («в палитре сайта его нет, не придумывай»), заменено на `--color-red-dark`. Урок: **перед тем как красить новый элемент — сверяться со списком переменных в `global.css` (`:root`), не подбирать "подходящий" цвет на глаз.**

**`ArticleCard.astro` — фон `.text-panel` теперь `var(--color-pastel-blue)` для ВСЕХ карточек ленты** (не только Koleston) — это глобальное изменение компонента, подтверждено пользователем 2026-08-17 по скриншоту. Если для конкретной статьи нужен другой фон текстового блока — потребуется отдельный вариант/проп, сейчас его нет.

**Обложка статьи (`coverImage` = один файл на карточку ленты + шапку страницы статьи) — стандарт решён 2026-08-17:**

Товар крупный (высота ~590 из 630px канвы), с отступом сверху ~30px — без отступа при hover-zуме карточки (`transform:scale(1.05)` в `ArticleCard.astro`) верхушка флакона визуально «выходит» за рамку.
- Старый градиентный баннер v2 (цветной градиент слева + текст + товар справа, из `[[brand-pdf-to-telegram-workflow]]`) — **больше не используется для новых обложек**, применялся только для самых первых версий до 2026-08-17.
- `.cover-overlay` (тёмный градиент поверх обложки на странице статьи, в `[id].astro`) был почти чёрным (rgba до 0.55) — с белым фото это выглядело грязным серым пятном. Облегчён до едва заметной тени только у нижнего края (`transparent 75% → rgba(43,32,28,0.08) 100%`), чтобы не пачкать белый фон.
- Скрипт сборки обложки (белый канвас 1200×630 + product-фото по центру, PIL) — референс сохранён в `Site/_tmp_koleston2/` и `Site/_tmp_colortouch2/`, не удалять.

**Шапка страницы статьи (`[id].astro`, банер над `<h1>`) — отдельный от `coverImage` элемент, готово 2026-08-18:** раньше `.cover` показывал `coverImage` как фон (растянутое фото товара) — теперь фон однотонный/градиентный по полю `accent` (`content.config.ts`: `z.enum(['blue','red']).default('blue')`, обязательно проставлять в каждой статье), а поверх — лого-«булька» Zilma (тот же приём, что в `Hero.astro`: белый halo + кольцо box-shadow + `logo.jpg`), включая ту же анимацию проявления `zilma-wipe` (диагональный mask-wipe, 2.1s). **Карточка в ленте (`ArticleCard.astro`) не тронута** — там по-прежнему настоящее фото товара из `coverImage`.
- `accent` подтверждён для всех 4 готовых статей: Koleston Perfect → `blue`, Illumina Color → `blue`, Color Touch → `red`, Shinefinity → `red`. Для новых статей выбирать по цветовой ассоциации линии/бренда, не наугад.
- Точные финальные размеры/позиция (подобраны итеративно по разметке пользователя на скриншоте, не менять без явной новой просьбы): `.cover-art` — `width: clamp(180px, 20vw, 210px)`, `aspect-ratio: 1`. `.cover-inner` — `position:absolute; height:260px` (высота самого `.cover`), `display:flex; align-items:center; justify-content:flex-end` внутри `.container` (совпадает с правым краем контента, как `.hero-art` в Hero) — за счёт `align-items:center` отступы сверху/снизу от границ фона всегда одинаковые на любой ширине экрана, магических margin-top больше нет.
- `.cover-inner` — **сиблинг `.cover`, а не потомок** (обёрнуты в общий `.cover-wrap`), с `z-index:3` и `pointer-events:none`. Это намеренно: сам `.cover` держит `overflow:hidden` (чтобы не вылезал фон), но лого должно визуально ложиться поверх стыка баннера и белой карточки статьи (тонкий нахлёст на card ~20-25px) — если бы лого было внутри `.cover`, оно бы обрезалось по нижнему краю баннера. `pointer-events:none` — чтобы декоративный слой не перекрывал клики по ссылке «← Все статьи» и тексту под ним.
- Если появится третий акцентный цвет (не blue/red) — добавить оба места: enum в `content.config.ts` и класс `.cover-<цвет>` в `[id].astro`.

**SEO-теги (`src/layouts/BaseLayout.astro`).** Добавлены: `canonical`, полный Open Graph (`og:type/site_name/locale/title/description/url/image(+width/height)`, `article:published_time`/`modified_time` для статей), Twitter Card (`summary_large_image`), JSON-LD (`Organization` на главной, `Article` на страницах статей — даты publish/modified, `headline` полный, не обрезанный). `astro.config.mjs`: `site: 'https://www.zilma.pro'` + интеграция `@astrojs/sitemap` (генерит `sitemap-index.xml` автоматически при билде, ничего вручную поддерживать не нужно). `public/robots.txt` со ссылкой на sitemap.

Белые уголки-вырезы (декоративное скругление самой картинки) залиты фоновым красным через `ImageDraw.floodfill` от всех 4 углов (`thresh=130`) — без этого iOS/Android накладывали бы свою маску поверх уже скруглённого изображения и было видно белые огрызки по углам.

   - **На 16px (вкладка браузера) детали причёски/лица неизбежно сливаются в силуэт** — ограничение самого детализированного дизайна, не баг конвертации, предупредить пользователя если ещё раз спросит.

**PWA-установка (site.webmanifest, apple-touch-icon, service worker, iOS-теги) — сделано 2026-08-23, все файлы в `public/`:**
- `site.webmanifest`: `name`/`short_name` «Zilma», `display: standalone`, `background_color: #38628c` (синий Hero — так же используется как фон PWA-сплэш-скрина при первом открытии установленного приложения, НЕ то же самое что обычный favicon), `theme_color: #c8000f`, иконки с явным `purpose` (`any` = круглые красные, `maskable` = квадратные с запасом). **Почему два набора:** если дать Android только круглую иконку без `maskable`, его адаптивная система иконок накладывает СВОЮ маску поверх уже круглой картинки (двойное скругление, белые огрызки по краям) — с явным `maskable`-вариантом этого не происходит.
- Service worker (`public/sw.js`, регистрируется в `BaseLayout.astro` через `navigator.serviceWorker.register('/sw.js')`) — простая network-first стратегия с офлайн-фолбэком на кеш для GET-запросов своего домена, **`/api/*` и не-GET запросы явно исключены** (заявки из `OrderForm` должны всегда идти живым запросом на сервер, не подменяться кешем). Технически с 2022-2023 (Chrome 108/112) service worker больше не обязателен для простой установки через меню браузера, но нужен для «богатого» автоматического диалога установки и для любой офлайн-устойчивости вообще.
- iOS-мета-теги (`apple-mobile-web-app-capable`, `-status-bar-style: default`, `-title: Zilma`) — без них ярлык на iOS открывался бы просто как вкладка Safari с адресной строкой, а не как отдельное приложение.
- **`src/components/InstallPrompt.astro`** — баннер снизу экрана (сайт-вайд, подключён в `BaseLayout.astro`), предлагает установку явно, а не полагается на то что пользователь заметит мелкую иконку в адресной строке Chrome:
  - Android/Chromium: слушает `beforeinstallprompt`, показывает кнопку «Установить», по клику вызывает системный диалог установки (`deferredPrompt.prompt()`). Эта кнопка — не своя логика, а обёртка над реальным браузерным API; появляется, только если браузер сам решил, что сайт достоин установки (это нельзя обойти кодом).
  - iOS (Safari **и** Chrome — на iOS Chrome тоже работает через WebKit по требованию Apple, у него нет `beforeinstallprompt`): показывает статичную инструкцию «Поделиться → На экран Домой» — единственный возможный вариант, программной установки на iOS не существует в принципе.
  - Скрыт, если уже запущено в standalone-режиме (уже установлено). Закрывается крестиком на текущую сессию браузера (`sessionStorage`, не `localStorage`) — при новом визите показывается снова, пока не установят.
  - **Ограничение, которое НЕЛЬЗЯ починить кодом:** уже установленные на телефон ярлыки/иконки не обновляются сами при смене дизайна — иконка «вшивается» в момент установки. Единственный способ увидеть новую иконку — удалить старый ярлык и установить заново. Предупреждать об этом пользователя каждый раз при смене фавикона/иконок после того, как он уже что-то устанавливал.

**Грабли сессии, которые стоит помнить:**
- **Атрибут `hidden` не работает, если у элемента есть свой `display`.** Плашки гидов помечались скрытыми и продолжали висеть на экране. Нужен явный `[hidden] { display: none }`.

- **`:has()`-правила писать через прямого потомка (`>`)**, иначе с ростом вложенности они проваливаются вглубь: правило «спрятать соседние линейки» приняло открытый бренд за линейку и опустошило папку.

## Редизайн главной и каталога — разбор концепта (2026-09-04)

Пользователь прислал сгенерированный макет (ChatGPT, файл `ChatGPT Image 4 сент. 2026 г., 21_54_42.png`) и попросил оценить, что взять и чем дополнить. Ниже — итог разбора, чтобы не пересобирать его заново в следующей сессии.

**Что из макета решено взять:**
- **Поиск в шапке** («по товару, бренду или линейке»). Сейчас нечёткий поиск заперт внутри окна каталога — снаружи его не найти.
- **Страницы брендов со своим URL** + левый список категорий + блок «О бренде» + хлебные крошки. Пересекается с уже записанной идеей «Полноценный каталог с фильтрами и своими URL на бренд» и напрямую отвечает на подтверждённую находку «сайт не находится в поиске»: модалка не индексируется, отдельная страница — да.
- **Блок «Не нашли нужный товар?»** с быстрой формой прямо в каталоге бренда — под позиции «под заказ», которые сейчас теряются.
- **Компактные чипы доверия** в хиро (у нас это уже есть блоком «Почему заказывают у Zilma», в макете свёрнуто в строку).

**Что решено НЕ брать и почему:**
- **Карточки товаров с фото и «избранное»** — упирается в отсутствие фото (см. отдельный раздел ниже), а «избранное» это отдельная фича с хранением.
- **Розово-скруглённая дизайн-система макета** — прямо противоречит тому, к чему пришли 2026-09-04 (прямоугольная геометрия, без заливок, прайс красный / инфо синий). Брать из макета структуру, но рисовать в нашей палитре и геометрии.
- **Товарный хиро** — наш хиро с анимацией лого зафиксирован как финальный, не трогать без отдельной просьбы.
- Два поиска на одном экране (в шапке и внутри бренда) — избыточно.

**Что я (Claude) предложил добавить сверх макета, по убыванию ценности:**
1. **Сквозной поиск по коду оттенка.** Мастер печатает `8/38` и получает сразу: позицию в прайсе с ценой и наличием, кружок-образец цвета и раздел статьи, где оттенок разобран. Связка «палитра ↔ живой прайс» есть только у нас (693 оттенка из 761 с реальными фото) — конкурент это не воспроизведёт. Данные уже все есть, сложность средняя.
2. **Честная замена оттенка, когда его нет в наличии.** Опирается на [[reference_wella-family-shade-codes-match]]: Koleston, Color Touch и Londa совпадают по номеру И цвету, значит при отсутствии 7/18 Koleston можно честно предложить Londa 7/18 с кнопкой заказа. Сейчас человек видит серый кружок и уходит. **Illumina и Shinefinity в подмену не включать** — другая технология. Сложность средняя.
3. **Фильтр «только то, что в наличии» над сеткой оттенков** — одна кнопка, сложность низкая.
4. **«Повторить прошлый заказ»** — хранить последние 2-3 отправленные заявки в localStorage (там же, где корзина) и давать повтор в один клик. Без базы и личного кабинета. Сложность низкая, ценность для постоянного B2B-клиента высокая.
5. **«Что изменилось в прайсе»** — по образцу уже работающего журнала `price-first-seen.json` отслеживать изменения цены и показывать «подешевело/подорожало с прошлого обновления». Сложность средняя.
6. **Мини-расчёт количества** (мастер думает «на 5 окрашиваний», а не «3 тубы») — пропорции с окислителем уже расписаны в статьях. Сложность средняя, это уже «на потом».

**Рекомендованный порядок:** страницы брендов + сквозной поиск по коду + честная замена оттенка — три вещи бьют в одну точку (пришёл из поиска по «Wella 8/38 купить» → страница бренда → нашёл оттенок → если нет, сразу видит рабочую замену). Начинать с ОДНОГО бренда целиком (Wella или Lebel — у обоих есть готовые гиды), посмотреть вживую, потом тиражировать на остальные 15.

**Шаг ноль, до всего остального:** ~~Яндекс.Метрика с целями всё ещё не заведена~~ — **счётчик установлен 2026-09-06** (детали выше, в разделе KPI). Осталось создать 4 цели в интерфейсе Метрики и включить Вебвизор — это делает пользователь. **Приоритеты по этому разделу пересматривать не раньше, чем накопятся первые данные**: до сих пор любой порядок работ был догадкой, теперь через пару недель будет видно, где люди реально отваливаются.

# Прокрутка широких таблиц — видимая и кнопкой (2026-09-11)

Повод — переписка с клиенткой: «объёмы разные, а цена одинаковая?». На телефоне в кадр
попала колонка «Артикул», номер прочитался как цена. Серая подсказка про прокрутку была на
экране и не помогла. Формулировка пользователя: **люди не читают, они видят то, что
бросается в глаза.**

Сделано в `[id].astro` (общее для всех статей, таблиц 19): подсказка синяя и жирная со
движущейся стрелкой; у правого края затухание в фон; **кнопка прокрутки на уровне ШАПКИ
таблицы** (посреди строк её принимали за кнопку у товара и она закрывала цену), клик листает
на **половину видимой ширины** — при полном шаге колонка, на которую смотрел человек,
уезжает целиком; при первом появлении таблицы в кадре её содержимое сдвигается и
возвращается. Пульсация прекращается, как только таблицу тронули.

**Анимации прокрутки — только таймером.** И свой цикл на `requestAnimationFrame`, и штатный
`behavior: 'smooth'` ведёт компоновщик кадров, а он местами придушен: в автоматическом
браузере ни один из них не сдвинул таблицу ни на пиксель, то есть и проверить их нельзя.
Обычное присваивание `scrollLeft` срабатывает всегда и проверяется замером.

**Таблицы в карточки на телефоне НЕ переделывали** — решение пользователя. Вариант остался
в запасе: CSS + перенос подписей из `<thead>` в `data-label`, правится в одном месте, тексты
статей не трогает.
